## 本节目标

这是一份可以照着执行的上线清单。每一项都给出验证方式，**没验证过的项不算通过**。

## A. 构建与镜像

- [ ] 镜像能从干净目录重复构建：`git clone && docker compose build`
- [ ] 镜像使用不可变版本标签，不是 `latest`：`docker image ls`
- [ ] 容器内不是 root：`docker compose exec api whoami` 输出非 root
- [ ] 镜像内没有 `.env`：`docker run --rm 镜像名 ls -a /app`
- [ ] 声明了健康检查：`docker inspect --format '{{.State.Health.Status}}' 容器名`
- [ ] 有 `.dockerignore`，且排除了 `.venv`、`.git`、`.env`、`data`
- [ ] 改一行业务代码后重建，依赖层命中缓存（构建日志里是 `CACHED`）

## B. 配置与密钥

- [ ] `.env` 在 `.gitignore` 里：`git check-ignore -v .env`
- [ ] 仓库提供 `.env.example`，字段完整、值留空
- [ ] `SECRET_KEY` 是随机值，长度 ≥ 32 字节
- [ ] 生产与开发使用不同的密钥和数据库
- [ ] 应用启动时校验必需配置，缺失立即失败，而不是运行到一半才报错
- [ ] `docker compose config` 能展开所有变量，无空值

## C. 数据

- [ ] 数据库使用命名卷或宿主机目录，容器重建不丢数据
- [ ] 完成过一次备份：`docker compose exec -T db pg_dump -U $USER $DB > backup.sql`
- [ ] 在空库上成功恢复过备份，且数据完整
- [ ] 备份文件存到了另一台机器或对象存储
- [ ] 迁移命令独立执行，不在应用启动脚本里：`docker compose run --rm api alembic upgrade head`
- [ ] 数据库端口没有映射到宿主机公网：`docker compose ps` 中 db 无 `0.0.0.0:5432`

## D. 网络与 TLS

- [ ] 域名 A 记录指向服务器 IP：`dig +short example.com`
- [ ] 80 端口自动 301 到 443：`curl -I http://example.com`
- [ ] 证书链完整：`curl -vI https://example.com` 无证书错误
- [ ] 续期可用：`certbot renew --dry-run`
- [ ] 防火墙只放行 22/80/443：`ufw status`
- [ ] 代理传递了 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto`
- [ ] 上传大小限制符合业务：`client_max_body_size`
- [ ] 应用端口未对公网暴露：`ss -ltn` 中只有 22/80/443

## E. 运行与可观测

- [ ] 所有服务 `restart: unless-stopped`
- [ ] 应用日志输出到 stdout，`docker compose logs` 可见
- [ ] 配了日志轮转或外部收集，磁盘不会被日志写满：`df -h`
- [ ] 容器时区正确：`docker compose exec api date`
- [ ] 有 `/health` 端点，且检查了关键依赖（数据库）
- [ ] 设置了内存与 CPU 限制，避免一个服务拖垮整机
- [ ] 最低监控三件套：探活、错误日志、磁盘与内存告警

单机 VPS **不是高可用架构**。接受这个事实，然后用备份和快速重建来兜底，不要假装它能扛住机房故障。

## F. 安全

- [ ] 应用以非 root 运行
- [ ] SSH 只允许密钥登录，禁用 root 密码登录
- [ ] 系统与基础镜像定期更新
- [ ] 依赖漏洞扫描过一遍：`pip-audit` 或 `docker scout`
- [ ] 生产环境关闭调试、异常不返回堆栈
- [ ] 登录接口有限流或失败锁定
- [ ] 不返回密码哈希、内部路径、数据库错误原文

## G. 发布与回滚

- [ ] 发布前打数据库备份
- [ ] 发布命令固定成脚本或 Makefile，不靠记忆
- [ ] 镜像保留上一个可用版本
- [ ] 演练过一次回滚：切回旧镜像 + 恢复数据库（如需要）
- [ ] 发布后执行冒烟测试，而不是只看容器是 running

## H. 上线当天顺序

1. 配好 DNS，等待解析生效
2. 配置防火墙，只开 22/80/443
3. 拉代码，创建 `.env`，核对 `.env.example` 字段
4. `docker compose config` 检查变量
5. `docker compose build`
6. 执行数据库迁移
7. `docker compose up -d`
8. 申请 TLS 证书，重载 Nginx
9. 跑冒烟测试
10. 接入探活与告警

## I. 冒烟测试

- [ ] `curl -fsS https://example.com/health` 返回 200
- [ ] 注册 → 登录 → 带 token 发文 → 列表能看到，全链路通
- [ ] 无 token 发文返回 401，不存在路径返回 404，方法不对返回 405
- [ ] 错误密码登录失败，且提示不泄露账号是否存在
- [ ] 浏览器控制台无混合内容（Mixed Content）报错
- [ ] 服务器重启后 `docker compose up -d` 能自动恢复，数据仍在

## 结语

部署能力的分水岭不是「会不会敲 docker 命令」，而是**出事时能不能在十分钟内定位并恢复**。上面每一项的价值，都在那十分钟里。

如果这份清单只能保留三条，就留这三条：

1. 备份验证过恢复
2. 回滚演练过
3. 有探活和错误日志

其余都是锦上添花。
