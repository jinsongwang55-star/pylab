## 本节目标

在请求进入业务逻辑之前，把所有非法数据挡在门口。这正是 Pydantic 在 FastAPI 里做的事。

## 为什么在边界校验

如果校验散落在业务代码里：

- 每个函数都要重复判断
- 错误信息格式不统一
- 非法数据可能已经写进数据库

正确做法：**入口一次校验，内部信任类型**。

## Pydantic 的语义

```python
from pydantic import BaseModel, Field

class UserCreate(BaseModel):
    username: str = Field(min_length=3, max_length=20)
    email: str
    age: int = Field(ge=0, le=150)
```

FastAPI 会自动处理：

- 缺字段 → 422
- 类型不符 → 422
- 越界 → 422
- 多余字段默认忽略

422 是 FastAPI 对「请求体校验失败」的标准状态码；400 多用于业务规则不满足。

## 错误结构

好的校验错误要指出**哪个字段、为什么**：

```json
{
  "detail": [
    {"field": "username", "message": "长度必须在 3-20 之间"}
  ]
}
```

一次返回所有错误，而不是遇到第一个就停——用户不想改一个提交一次。

## 类型陷阱

Python 里 `bool` 是 `int` 的子类：

```python
isinstance(True, int)   # True
```

校验整数时要额外排除 bool，否则 `age=True` 会被当成 1。

## 练习

实现 `validate_user(payload)`：

- 返回 `(cleaned, [])` 或 `(None, errors)`
- `username`：str，去首尾空格，3–20 字符，只允许字母、数字、下划线
- `email`：str，去首尾空格，必须匹配 `xx@yy.zz`
- `age`：int（排除 bool），0–150
- 无关字段直接丢弃
- `errors` 是 `[{"field": 字段名, "message": 非空说明}]`，一次性收集全部错误

## 检查点

测试会检查：缺三个字段时 errors 是否同时包含三者、bool 是否被拒绝、多余字段是否被丢弃。
